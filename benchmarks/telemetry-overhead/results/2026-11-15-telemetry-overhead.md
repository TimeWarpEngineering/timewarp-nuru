## Analysis

Written by hand after the generated sections above (task 520).

### Per-run cost of `UseTelemetry()` (AOT)

| Case | Mean | Over case 1 |
|:---|---:|---:|
| 1 off | 4.1 ms | — |
| 2 on, no endpoint | 5.4 ms | +1.3 ms |
| 3 on, reachable (gRPC) | 1016 ms | +1012 ms |
| 3 on, reachable (http/protobuf) | 1014 ms | +1010 ms |
| 4 on, unreachable (closed local port) | 1015 ms | +1011 ms |

- **No endpoint costs about 1.3 ms.** The timeline puts only 0.06 ms of it between Main and the
  handler, so the rest is outside Main: loading a binary 2.5 times larger (4.7 MB to 12 MB) and
  static setup. Three extra 200-run passes gave +1.27, +1.30, and +1.33 ms.
- **An endpoint costs about 1.01 s, and the grace delay is 99% of it.**

### Case 3 breakdown (AOT, gRPC)

| Part | ms | Source |
|:---|---:|:---|
| Provider setup (tracer, meter, logger factory, OTLP exporters) | 4.8 | Main-to-handler, case 3 minus case 1 (4.84 − 0.03) |
| `FlushTelemetryAsync` grace delay (`Task.Delay(1000)`) | 1000 | fixed default |
| ForceFlush (export) and dispose | 3.2 | handler-to-exit minus case 1 minus 1000 (1003.28 − 0.09 − 1000) |
| Outside Main (bigger binary load, exporter threads at exit) | 4.0 | rest of the 1012 ms |
| **Total over case 1** | **1012** | hyperfine 1016 − 4.1 |

The grace delay is 1000 of 1012 ms (98.8%). Without it, an AOT run that exports to a local
collector would cost about 12 ms more than telemetry off. http/protobuf is about the same: flush
and dispose take about 2.3 ms. The receiver counted 1 trace export and 2 metric exports per run
(one at ForceFlush, one at dispose), and no log exports, because the command writes no log record.

### Failure path (case 4)

A closed local port costs the same as a reachable receiver (1015 ms): the connection is refused
at once, the export fails in about 2.5 ms, and the grace delay dominates again. A **blackholed**
endpoint, where packets are dropped instead of refused, behaves differently. It is not in the
script; one-off runs against `http://192.0.2.1:4317` (TEST-NET-1) took **17.0 s** per run with
the default exporter timeout, 4.0 s with `OTEL_EXPORTER_OTLP_TIMEOUT=1000`, and 6.0 s with 2000.
Filed as task 590, together with skipping the grace delay after a successful ForceFlush.

### AOT against JIT (and 517)

| Case | AOT | JIT | 517 (JIT) |
|:---|---:|---:|---:|
| 1 off | 4.1 ms | 30.5 ms | — |
| 2 on, no endpoint | 5.4 ms | 37.0 ms | 34–36 ms |
| 3 on, reachable (gRPC) | 1016 ms | 1224 ms | 1187–1208 ms |
| Provider setup in case 3 | 4.8 ms | 129 ms (144.1 − 15.4) | 117–122 ms |
| Flush and dispose in case 3 | 3.2 ms | about 52 ms | 41–52 ms |

517 attributed its ~120 ms of provider setup mostly to first-run JIT. AOT confirms it: setup
drops from 129 ms to 4.8 ms. A daemon-hosted provider would save at most about 8 ms per AOT run
(setup plus flush), so it is not worth building for that reason. The grace delay is the
only large cost left.

### Is it stable enough for CI (501)?

On this machine, yes for coarse checks. The AOT cases have σ of 0.2 to 0.3 ms with min and max
within 2 ms of the mean, and the endpoint cases have σ ≤ 1 ms. Repeated passes moved the means
by less than 0.2 ms. GitHub-hosted runners are shared VMs, so absolute millisecond thresholds
would flake there. Two checks would hold up:

- case 2 minus case 1 (AOT) under a few ms, which catches a return of the 1 s no-endpoint delay
  (517) or JIT-sized setup;
- case 3 under a ceiling, about 1.1 s now and much lower after 590.

Cost: two AOT publishes (about 1 to 2 minutes) plus hyperfine on the runner. Not added to CI here.

### Other observations

- `ICSharpCode.Decompiler.dll` (3 MB) lands next to both AOT binaries. It comes from the
  analyzer project's `CopyToOutputDirectory` item, which flows through the in-repo analyzer
  `ProjectReference`. NuGet consumers get it only under `analyzers/`, the AOT binary never loads
  it, and it does not affect these timings. No task filed.
