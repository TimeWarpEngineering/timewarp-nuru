## Prior findings
### M1 — Severity: bug — Status: fixed
- Verification: `nuget-version-service.cs:164` now reads `if (index?.Versions is not { Count: > 0 } versions) throw new HttpRequestException(..., response.StatusCode)`. This covers a null body (`index` null), `{}` (`Versions` defaults to `[]`, so Count 0), `{"versions":[]}` and `{"versions":null}` (`Versions` null fails the property pattern). The pattern compiles: `Count` resolves through `IReadOnlyCollection<T>`, which `IReadOnlyList<T>` inherits, and `versions` is definitely assigned (typed `IReadOnlyList<string>`) on the fall-through path. Tests `Empty_object_body_on_success_throws` and `Empty_versions_array_on_success_throws` pass. False-positive check: unlisted versions stay in the flat-container index, so a package with every version unlisted still returns a non-empty array. An unknown id returns 404. The only case where an existing id could plausibly return 200 with an empty array is an admin hard-delete of every version. Throwing there is the correct direction for a release gate: it blocks and never approves, and nuget.org does not allow a deleted version number to be pushed again. This is not a defect.
### M2 — Severity: suggestion — Status: fixed
- Verification: `JsonException` from `DeserializeAsync` is wrapped at `:154-159` in `HttpRequestException` (status 200, inner exception kept). `SendAsync` at `:179-189` catches `OperationCanceledException` only when `!cancellationToken.IsCancellationRequested`. In .NET 5+ (including .NET 10), when `HttpClient.Timeout` fires, `HttpClient` throws `TaskCanceledException` with an inner `TimeoutException`, and the caller's token is NOT cancelled. So the filter matches a real timeout and wraps it as `HttpRequestException(RequestTimeout)`. When the caller cancels, `IsCancellationRequested` is true, the filter is false, and the OCE propagates unchanged. If the caller cancels at the same moment a timeout fires, the OCE also propagates, which is the correct outcome. The body read and deserialize run after `GetAsync` has buffered the whole response (the default `ResponseContentRead`), so `SendAsync` is the only place a client timeout can occur. `HttpRequestException` from the handler (DNS, connection refused) is not caught by the filter and still reaches the callers' catch directly. Both callers (`check-version-command.cs:133`, `release-command.cs:321`) catch `HttpRequestException`, so every lookup failure now takes the graceful fail-closed path. One caveat: `Client_timeout_throws_http_request_exception` simulates the timeout by throwing TCE from the stub handler rather than letting `HttpClient.Timeout` expire. It still exercises the same filter branch, because `HttpClient` rethrows handler OCEs unchanged when neither its timeout nor the caller token has fired. `Caller_cancellation_propagates` covers the other branch.
