# DevCli content must not raise CA1034 or CA2000 in a consumer

## Description

TimeWarp.Nuru.DevCli content is compiled into the consumer. 4.0.0-beta.9 still raises two analyzer codes there, so consumers keep `NoWarn` entries that exist only for package content.

- **CA1034** — nested `Handler` in four content files:
  - `source/timewarp-nuru-devcli/content/any/endpoints/clean-command.cs`
  - `source/timewarp-nuru-devcli/content/any/endpoints/release-command.cs`
  - `source/timewarp-nuru-devcli/content/any/endpoints/check-version-command.cs`
  - `source/timewarp-nuru-devcli/content/any/endpoints/self-install-command.cs`
- **CA2000** — `new HttpClientHandler` in `NuGetVersionService()` (`source/timewarp-nuru-devcli/content/any/services/nuget-version-service.cs`). The handler is owned by the service, but the analyzer does not see that transfer.

Nuru 558 kept CA1034 as a repo preference (`.editorconfig` sets `dotnet_diagnostic.CA1034.severity = none` because nested types encapsulate handlers). That file does not ship inside the package. A consumer whose own `.editorconfig` leaves CA1034 at its default sees the four nested handlers. The same 558 Results list CA2000 as remaining when dev-cli `NoWarn` is cleared.

Fix the content. **No suppression of any kind** (Steve 2026-10-30, 558: "i don't want us to supress the damn thing either"): no `#pragma`, `[SuppressMessage]`, content-scoped globalconfig, `// <auto-generated/>` header or package `.editorconfig`. A consumer build that does not copy Nuru's `.editorconfig` or `NoWarn` must be clean for CA1034 and CA2000.

## Requirements

- A consumer project that compiles DevCli content, with CA1034 and CA2000 at warning and absent from `NoWarn`, builds with neither code.
- Nuru may keep CA1034 off inside this repo. Package content must not depend on that preference.
- Do not ship a package `.editorconfig` that turns those rules off for the whole consumer project.
- **CA1034: make every DevCli content type `internal`** (Steve 2026-10-30: "2, they will break consumers which
  is great"). Keep handlers nested; nesting is the point (encapsulation). Every top-level and nested type
  under `source/timewarp-nuru-devcli/content/` goes from `public` to `internal`. DevCli ships no compiled
  library (`IncludeBuildOutput=false`): `build/TimeWarp.Nuru.DevCli.props` compiles the files into the
  consumer's own project, so nothing outside that assembly can reference them.
  - Confirm the Mediator source generator still discovers and dispatches `internal` handlers. Build and run
    the DevCli tests. If it does not, stop and record why. Do not suppress.
  - Fix Nuru's own consumers of the content the same way. That is `tools/dev-cli` (its public types that
    expose DevCli types in public signatures become `internal`, as `workflow-command.cs` Handler already is)
    and the tests that compile the content.
- CA2000: restructure `NuGetVersionService()` so ownership is visible to the analyzer. For example, create the handler in a local, pass it to `HttpClient(handler, disposeHandler: true)` inside try/catch that disposes the handler on failure, or use a factory the analyzer accepts.
