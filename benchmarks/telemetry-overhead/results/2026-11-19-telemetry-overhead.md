## Analysis

Written by hand after the generated sections above (task 590). Baseline: the 2026-11-15 run
(task 520), which had the fixed 1 s grace delay in `NuruApp.FlushTelemetryAsync`.

### What changed

`FlushTelemetryAsync` no longer calls `ForceFlush()` and then waits 1000 ms. It calls
`Shutdown(budget)` on the tracer and meter providers and disposes the logger factory, all three
in parallel, and waits at most the budget: 2000 ms by default, or `OTEL_EXPORTER_OTLP_TIMEOUT`
when that is set. Shutdown exports what is buffered and returns when the export has finished, so
no exporter needs time after it (517 follow-up a).

### Per-run cost of `UseTelemetry()` (AOT)

| Case | 2026-11-15 | This run | Over case 2 now |
|:---|---:|---:|---:|
| 1 off | 4.1 ms | 4.5 ms | — |
| 2 on, no endpoint | 5.4 ms | 5.8 ms | — |
| 3 on, reachable (gRPC) | 1016 ms | 13.1 ms | +7.3 ms |
| 3 on, reachable (http/protobuf) | 1014 ms | 12.7 ms | +6.9 ms |
| 4 on, unreachable (closed local port) | 1015 ms | 12.3 ms | +6.5 ms |
| 5 on, blackholed (gRPC, default) | about 17 s (one-off) | 2.01 s | budget |
| 5 on, blackholed, `OTEL_EXPORTER_OTLP_TIMEOUT=500` | — | 0.51 s | budget |

- **Case 3 is now within about 7 ms of case 2.** The timeline puts 4.9 ms in provider setup
  (Main to handler, case 3 minus case 2) and 1.3 to 1.6 ms in shutdown and dispose. The grace
  delay is gone.
- **A blackholed endpoint costs the budget and no more.** The default run takes 2.01 s against
  about 17 s before; with `OTEL_EXPORTER_OTLP_TIMEOUT=500` it takes 0.51 s, so a user-set timeout
  still applies. The export threads are background threads, so the process exits at the budget
  even though the export has not returned.
- **The JIT build also drops**, from 1224 ms to 228 ms for case 3 over gRPC.

### Receiver export counts

Each run now sends 1 trace export and 1 metric export (gRPC 66 = 33 AOT + 33 JIT runs; HTTP 33).
The 2026-11-15 run sent 2 metric exports per run: one at `ForceFlush` and one at dispose. Shutdown
collects and exports metrics once.
