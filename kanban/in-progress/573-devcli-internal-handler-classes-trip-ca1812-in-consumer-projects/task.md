# DevCli internal Handler classes trip CA1812 in consumer projects

## Description

TimeWarp.Nuru.DevCli ships its code as source (`source/timewarp-nuru-devcli/content/any/**/*.cs`), so it
compiles under the **consumer's** analyzer rules. Task 558 set the rule: DevCli's shipped source is never
the cause of a consumer diagnostic, and it is never hidden by suppression.

Four shipped endpoint handlers are `internal sealed class Handler` (made internal by 560 to clear CA1034):

- `content/any/endpoints/release-command.cs:85` — `ReleaseCommand.Handler`
- `content/any/endpoints/self-install-command.cs:26` — `SelfInstallCommand.Handler`
- `content/any/endpoints/check-version-command.cs:63` — `CheckVersionCommand.Handler`
- `content/any/endpoints/clean-command.cs:22` — `CleanCommand.Handler`

The mediator activates them, so the compiler sees no instantiation and CA1812 ("internal class that is
apparently never instantiated") fires in the consumer. With `TreatWarningsAsErrors` that breaks the
consumer's dev-cli build.

Nuru does not see this because its root `Directory.Build.props:69` has `CA1812` in `NoWarn`
("False positives for DI-instantiated classes").

Evidence (2026-11-11, timewarp-multiavatar task 006, DevCli 4.0.0-beta.12): after
`ganda repo audit --fix` generated `tools/dev-cli`, the build failed on CA1812 for these four types. The
only consumer-side workaround is four assembly-level `[SuppressMessage]` attributes
(`tools/dev-cli/endpoints/suppressions.cs`), which then fails the `analyzer-suppressions` audit check as
above the baseline. timewarp-amuru carries CA1812 entries in its suppression baseline for the same
pattern. Every repo that takes the generated dev CLI hits this.

## Requirements

- A consumer with CA1812 enabled and warnings as errors compiles the DevCli content with no CA1812 and no
  consumer-side suppression.
- Per 558: no `// <auto-generated/>` header, `#pragma warning disable`, `[SuppressMessage]`, or
  globalconfig in the shipped content. The code itself must pass the rule.
- Do not regress 560: no CA1034 or CA2000 for consumers.
- Check every shipped content type, not only the four listed (other mediator- or DI-activated internal
  classes may have the same problem).
- Add a regression gate: compile the DevCli content with CA1812 on (Nuru's own `NoWarn` hides it today).

## Goal (implementer restatement)

## Results

### Reproduction

With CA1812 enabled in `tests/devcli-consumer-check`, exactly four shipped content types fired,
the four the description lists: `CheckVersionCommand.Handler`, `CleanCommand.Handler`,
`ReleaseCommand.Handler`, `SelfInstallCommand.Handler`. No service or other content type fired;
the generator already builds the content services and commands with `new`.

### Cause

The TimeWarp.Mediator generator registers each nested handler as `AddScoped<Handler>(services)`.
The container builds it by reflection, so no `new Handler(...)` appears in the compilation.

### Fix (generator, no change to the shipped content)

- `EndpointExtractor.IsFactoryConstructible` flags a nested `[NuruRoute]` Handler declared in
  this compilation, not abstract or generic, with exactly one public constructor whose
  parameters are all required (no default, `params` or `ref`). Model field:
  `HandlerDefinition.NestedHandlerFactoryConstructible`.
- `interceptor-emitter.handler-factories.cs` emits `__UseHandlerFactory<THandler>` and, right
  after `AddGeneratedMediator(services)` in both the source-gen mediator container and the
  runtime-DI container, one call per flagged handler:
  `__UseHandlerFactory<H>(services, static sp => new H(GetRequiredService<T1>(sp), ...))`. It
  replaces the mediator's own descriptor with the same lifetime (it only swaps a non-keyed
  descriptor whose implementation type is the handler, and adds nothing otherwise). That matches
  how the container builds a single-constructor type, so dispatch does not change. Registrations
  made later (a runtime-DI app's `ConfigureServices`) still win. The explicit `new` in the
  generated code is what CA1812 counts.
- Handlers the container could build another way (several public constructors, optional
  arguments) keep the reflection registration.
- Shipped content is unchanged: still `internal sealed class Handler` (no CA1034), no pragma,
  `[SuppressMessage]` or `<auto-generated/>`. The consumer check also runs CA2000 and CA1034
  (AnalysisMode All, warnings as errors) and passes.

### Regression gate

- Root `Directory.Build.props` adds CA1812 to NoWarn only when `NuruConsumerCheck` is not
  `true` (same per-file suppression count). `tests/devcli-consumer-check/Directory.Build.props`
  sets `NuruConsumerCheck=true` before its import, so the check (CI samples stage,
  `workflow.yml` "DevCli consumer check") compiles the content with CA1812 on.
- Negative check: with the factory emission disabled, the consumer check fails with CA1812 on
  all four handlers; restored, it passes.
- `tests/timewarp-nuru-tests/generator/generator-73-nested-handler-factories.cs` (Roslyn-hosted,
  standalone list + CiTestExcludes): factory emitted with resolved arguments, emitted after
  `AddGeneratedMediator`, a zero-dependency handler uses `static _`, skipped for two
  constructors and for an optional argument, none without a generated mediator.
